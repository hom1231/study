\* \[ 32주소의 세 조각 ] : 32bit 주소의 세 조각 **\[PGD 인덱스 10bit}] \[ PTE 인덱스 10bit] \[ offset 12bit]**

=큰 지도 몇 칸, 작은 지도 몇 칸, 페이지 안 몇 걸음



ex) 가상 주소가 0x00C0\_1234일 때 0000 0000 11/00 0000 0001/ 0010 0011 0100

PGD 인덱스 = 3, PTE 인덱스 = 1, offset 12bit =0x234



왜 10bit 인가?

\*\*표(PGD,PTE)\*\*도 4KB 페이지 1장:4KB / 엔트리 4B = **1024칸** = 10bit 산수다.



walk와 TLB

초기 표 2장(PGD,PTE) 걷기(walk)= RAM 접근 2회 추가→

이후 TLB(지름길캐시)가 접근 횟수 0회로(바로 offset으로)



**특정한 주소를 넣었을 때 빠르게 찾아내는 것 Interval Tree**



프로세스마다 자기 PGD가 있다

**같은 가상 주소** > **다른 물리 frame**

이게 격리 - 남의 메모리에 닿을 수 없다.



가상 메모리가 주소 받음 > pgd 확인 결과 P=0 > Page Fault(페이지가 없다) >

OS가 **buddy**에서 frame 받아 채우고 재시도

내 땅이 아예 아님(**find\_vma 미발견**) > **SIGSECV** - 프로그램 강제 종료



\* \[ LRU ] :

&#x20; > 활용 예시 : 사용 순서가 p\[0] > p \[1] > p\[2] > p\[3]> p\[1]>p\[2]>p\[4] 일 때

제일 오랜 시간 쓰지 않은 p\[2]가 swap out, 새로운 페이지가 swap in 된다.



RAM이 모자라면 - 두 줄의 LRU와 second chance

리눅스의 근사 LRU 진짜 LR는 불가능 > MMU가 켜 주는 R비트 +active/inactivr 두 줄

회수(kswap} inactive 꼬리부터: R=1 기회 한 번 더 (머리로)/R=0>축출(dirty면 write-back 먼저)



주소 공간에 표를 겹겹이 쌓는 이유는 **메모리를 절약**하기 위해서 및

실제 프로세스가 사용하는 주소 공간에 비어 있는 구멍이 크게 존재하는 **희소성**(Sparsity) 성질 때문이다.





\* \[ 터미널 속 ls 처리 ] : **bash가 자신을 복제(fork) > 자식이 ls로 변신(execve) > cpu 차례로 배정(스케줄러 CFS) >**

**주소를 표로 변환(MMU \[ PGD > PTE ] ) > 첫 접근 페이지 적재(#PF+buddy > 좀비 회수 prompt 복귀(wait)**

\* \[ fd 테이블 ] : 0,1,2는 키보드 모니터, 버퍼링 없는 모니터로 이미 사용 중이므로

**3부터 사용 가능한 파일** 등장

인터럽트(interrupt) 발생 시 익셉션(exception) 발생 시 system call 호출 시



\* \[ struct file ] : current 포지션을 관리하는 것이 **file**(f\_pos)

**역할 :** 연 파일의 이름 관리(d\_name) 및 다음 구조체 지목



\* \[ dentry ] : **경로 조각 '/', 'home', 'user', 'a.txt'를 하나씩 짚어가는 커널 자료구조**

**역할 :** 연 파일의 이름 관리(d\_name) 및 다음 구조체 지목



\* \[ inode ] : **권한·크기·블록 위치를 갖고 있어서 '파일의 본체'라 부를 수 있는 자료구조**

이름을 제외한 모든 정보가 모두 있다

|i\_perm|i\_nlink|i\_uid|i\_gid|i\_size|i\_mtime|i\_data\[0]|i\_data\[12]|
|-|-|-|-|-|-|-|-|
|"-rw-rw-r--"|1|linux|linux|6|Sep 1|4K|용량 추가|



**없는 파일을** open하면 **반환값은 -1**이고 **errno은 ENOENT**



\* \[ rm과 close ] :

**rm**은 '지우기'가 아니라 '**이름표 떼기**', **dentry의** **정보만을 삭제**하여 inode와 fd 테이블 정보가 모두 남아있다.

**struct file이 inode와 블록을 잡아둔다**.



**rm 한 뒤 ls -l /proc/<PID>/fd 에 파일명(dentry) 옆에 (deleted)가 붙는다**.



**close(n)** 는 **fd 테이블의 n번 슬롯을 비워** **struct file**의 참조수를 0으로 만들어 **해제** 시킨다.

그래서 연결은 끊기지만 **inode와 블록 dentry**는 그대로이다.



\* \[ **read**() ] : open과 같이 file > inode로 향하다 페이지 캐시를 확인한다. 미스(없을)시 디스크에서 읽는다.

이후는 캐시를 읽어 **디스크를 거치지 않고** 바로 읽는다.



\* \[ **write**() ] : write(3, "new", 3): fd → struct file → inode → **페이지 캐시**의 **페이지 0**

페이지 0의 내용을 **메모리에서 바꾸고 dirty 표시를 붙인다**. >

**write는 여기서 반환**(마이크로초). 프로세스는 '저장됐다'고 믿지만 **디스크에는 없다**. >

**30초 후 writeback 스레드가 깨어나** dirty 페이지를 모아 **디스크로 내려**보낸다.

\- writeback **전에 끄면 저장 X** 'hello' 유지

**디스크 블록이 'new'가 되고 dirty 표시가 지워진다**.



\* \[ **fsync**(n) ] : **n 파일의 dirty 페이지**를 **즉시** 내리라는 명령으로 **페이지 0의 내용을 블록으로 내린다**.



\* \[ **dup2**( n, 1 ) ] : **1번 슬롯의 화살표를 n번이 향하는 곳(out.txt로 가정)으로 바꾼다**.

&#x20; > 활용 예시 : close(n) 이후 1 번만 out.txt를 가리킨다. **>**

execve로 자식을 ls로 바꾸면 프로그램은 바뀌나 fd 테이블은 유지된다. **>**

ls는 평소처럼 fd 1(모니터)에 write 한다. **>** 그 경우 ls의 출력이 out.txt로 향한다.

■ 3. 에러 노트 (Troubleshooting)

\--------------------------------------------------

***프로세스 A와 B가 같은 가상 주소를 읽어도 서로 다른 데이터가 나오는 직접적인 이유는?***



1 가상 주소가 실행마다 무작위로 바뀌기 때문
2 물리 RAM이 프로세스별로 물리적으로 분리되어 있기 때문
3 CR3가 가리키는 PGD가 프로세스마다 다름
4 TLB가 프로세스마다 하나씩 있기 때문





**답:3**

**CR3가 가리키는 PGD가 프로세스마다 다름 —**

**컨텍스트 스위치 때 CR3가 그 프로세스의 PGD로 바뀐다 →**

**같은 가상 주소가 다른 물리 frame으로 변환 = 격리.**





***refault란?***



1 축출된 페이지를 다시 접근해 재적재하는 것

2 TLB 미스로 페이지 테이블 walk를 다시 하는 것

3 페이지 테이블이 두 번 만들어지는 것

4 fork 직후 자식이 처음 실행되는 것





**답:1**

**회수 오판의 청구서: 쫓아낸 페이지를 다시 쓰면 디스크에서 재적재(수만 배 느림).**





***`open()` 시 파일 권한 검사가 일어나는 지점과 실패 시 결과는?***



dentry 탐색 단계 · errno=ENOENT

fd 테이블 빈 슬롯 할당 단계 · errno=EMFILE

inode 권한 검사 · errno=EACCES

페이지 캐시 조회 단계 · errno=EIO





답:3

**이름 찾기는 dentry, 권한은 inode. 커널이 검사하며 실패 시 -1/EACCES → 셸의 Permission denied.**





***`write()`가 반환된 뒤 dirty 페이지를 디스크로 내려보내는 주체가 아닌 것은?***



writeback 커널 스레드

fsync() 시스템 콜

copy\_to\_user()

sync 명령





**답:3**

**copy\_to\_user는 read 경로에서 페이지 캐시 → 유저 버퍼 복사. 디스크 쓰기와 무관.**





***`write()`가 성공(3 반환)한 직후 전원이 끊기면 데이터가 사라질 수 있는 이유는?***



write가 디스크에 쓰는 도중에 중단되기 때문

inode가 아직 생성되지 않았기 때문

dentry 캐시가 사라지기 때문

dirty 페이지가 RAM에만 있어서





**답: 4**

**write는 페이지 캐시에만 쓰고 반환한다.**

**writeback 전에 RAM이 사라지면 디스크는 이전 값.**
